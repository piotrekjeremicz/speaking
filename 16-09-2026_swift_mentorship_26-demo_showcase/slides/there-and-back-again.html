4. "Fine — let's use p instead."
  p f.x → note: ran \`expression -- f.x\` / (Int) 42 — "It works — but look at that note. LLDB just JIT-compiled a tiny program and called the real getter, just to read one field."
  frame variable f._x → instant, no JIT — "Same value, zero compilation. That gap — x vs _x — is exactly what my project closes."

A Mental Model

Think Codable

DWARF is just another serialization format — for your program's shape, not its data.

Point at each row in turn. Say: "You already know this pattern from Swift — Encodable turns a struct into JSON, Decodable turns it back. DWARF works the same way, one level down: instead of encoding your data, it encodes your program's shape — its types, its properties, where things live in memory."
Encode · 01 — DWARF 6

A New Tag: DW_TAG_property

A data member you access like a field, but that's really backed by an accessor — with a pointer back to its real storage.

0x0000003c: DW_TAG_member
              DW_AT_name   ("_x")
              DW_AT_APPLE_property  (0x00000032 "x")

0x0000004a: DW_TAG_property            (0x4c)
              DW_AT_name   ("x")
              DW_AT_type   (0x000000a6 "NSInteger")

0x00000052:   DW_TAG_property_getter   (0x4d)
                DW_AT_property_forward  → 0x0000003c "_x"

real llvm-dwarfdump output — same Foo/x example as the demo, captured with the patched clang

Say: "DWARF version 6 defines a new tag: DW_TAG_property. It represents something you access like a field, but that's really computed by a getter — with a pointer back to where the real data lives. Before this existed, a debugger reading x had no way to know it actually meant _x." This is the whole idea in one DIE dump — everything else in the talk is "how do three different programs agree to write and read this." Mention here: I originally started this on Objective-C, not Swift — Clang already had a mature property model (DIObjCProperty) to build on, so it was the faster path to prove the design end-to-end.
Encode · 02 — LLVM IR & DWARF Emission

DIProperty

!9 = !DIProperty(name: "x", type: !7, backing_storage: !8)
PR #215776 · merged 4 commits 26 files

Plumbed through the parser, the writer, bitcode, the verifier, DIBuilder, and DWARF emission. Every mountain guards old gold — this time it was bitcode backward-compatibility.

Say: "My first job was teaching LLVM itself about this tag. I added a new metadata node, DIProperty, and plumbed it through every layer that touches debug info — the parser, the writer, bitcode, the verifier, and DWARF emission itself." Mid-review, adrian-prantl (LLVM debug-info maintainer) pushed back on how this should relate to the existing ObjC-specific node — real design debate, not rubber-stamping.
Encode · 03 — Clang

Teaching Clang to Say It

CGDebugInfo.cpp now emits DIProperty for synthesized Objective-C @property — three cases: a declared custom ivar, an undeclared one the compiler invents, and a fully implicit @synthesize.

PR #220362 · merged approved by Augusto 0 regressions / 7 existing tests
Goal: get a real compiler to actually emit the tag. Say: "Having the tag in LLVM means nothing if no compiler ever writes it. So next I taught Clang to emit DIProperty — for Objective-C properties, since Clang already understood that language's property model well. It covers three real cases: a custom-named ivar you declare yourself, one the compiler creates for you, and full auto-synthesis with no @synthesize at all." If time: the tag briefly "vanished" from a compiled object — turned out to be a stale local llvm-dwarfdump binary, not broken code. Caught it before it reached Augusto.
Decode · 01 — LLDB

Making LLDB Listen

DWARFASTParserClang now reads DW_TAG_property back and attaches the synthesized ivar to the property declaration — plus a new CompilerType::GetPropertyBackingStorageName.

in progress · committed locally, no PR yet
This is the reading half of the analogy — the Decodable side. Say: "Writing the tag is half the story — something has to read it back. This is where I taught LLDB's DWARF parser to recognize DW_TAG_property and attach the real backing ivar to the property it belongs to. This part is still in progress — working on my machine, but not a PR yet."
Decode · 02 — the "p" command

dwim-print Gets a Fast Path

dwim-print — "do what I mean, print" — tries frame variable first, and only falls back to a full JIT-compiled expression if that fails. Wiring in the new backing-storage info lets it succeed on the fast path for properties too.

work in progress · CommandObjectDWIMPrint.cpp

this is what you saw at the very start

Say: "Last step: LLDB knowing the link exists doesn't help unless a command actually uses it. dwim-print — that's what p really is — tries a cheap memory read first, and only falls back to a full JIT-compiled expression if that fails. I'm wiring the new backing-storage information into exactly that decision. This is what you saw right at the start — let's go look at it again, for real this time." Bridge line into demo 2.
